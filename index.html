nsrllookup is a forensic lookup API. It compares file hashes with the NIST Reference Data Set. Each answer shows the dataset that gave it.

Start the service → View on GitHub
Why nsrllookup

Remove the known files. Examine the remaining files.

A seized disk can contain one million files or more. Most of these files come from operating systems and standard software. They are not evidence. nsrllookup finds these files, so that you can put your time into the files that remain.

STEP 1

Calculate the hashes

Use your forensic tool to calculate an MD5, SHA-1 or SHA-256 hash for each file in the evidence.

→
STEP 2

Send the hashes

Send the hashes to nsrllookup. It compares each hash with the NIST list of files from published software.

→
knownPut the file aside.

NIST recorded this file in published software.

unknownExamine the file.

NIST has no record of this file. It can be user data, a custom file or malware.

NOTEA known result does not mean that the file is safe. It means only that NIST found the file in published software. An unknown result does not mean that the file is malicious.

Features

Answers that you can check.

01

Each answer shows its source

Each result shows the Set, the Release, the Delta releases and the final dbhash. Use these values to check the answer with NIST.

02

Three integrity checks

The Provisioner checks the archive SHA-1, the SHA-256 of each inner file and the NIST dbhash. If one check fails, the service does not use the data.

03

Public, with an audit record

The API does not require a login. The service records each lookup session in an append-only Audit Trail. This includes rejected sessions.

04

One service, low memory

One WSGI service reads a verified, read-only database. Each lookup reads an index on the disk. The dataset does not stay in memory.

Lookup Result

Each answer shows its source.

Send one Algorithm and one or more Digests. The service returns one result for each digest. Each result identifies the dataset.

  • ✓MD5, SHA-1 and SHA-256. Use uppercase or lowercase letters. The service changes all letters to uppercase.
  • ✓One result for each digest. If a digest is not correct, its result is invalid. The other digests receive a usual result.
  • ✓Readiness gate. If the manifest is missing or does not agree with the data, the service returns 503. It gives no answers.
POST /check

    -H 'Content-Type: application/json' \

Provisioning

Three integrity checks.

The Provisioner does the three checks below. It writes the three values into the Provisioning manifest. At startup, the service compares the manifest with the Hash Set. The service is ready only if they agree.

1

Archive SHA-1

The Provisioner compares the SHA-1 of the Release archive with the NIST .sha file.

2

Inner-file SHA-256

The Provisioner compares the SHA-256 of each file in the archive with signatures.txt.

3

Final dbhash

The Provisioner applies all Delta releases. Then it compares the database hash with the NIST dbhashes.txt value for the last Release.

NSRL coverage

Available data.

NIST supplies four Sets. nsrllookup uses one Set: Modern, in the Minimal form. The Minimal form is approximately 18 GB. The full Modern Set is approximately 124 GB. Delta releases update the data. You do not download the base Release again.

SetStatusForm
ModernServedMinimal (~18 GB)
LegacyLater—
AndroidLater—
iOSLater—
AlgorithmLookup
MD5Yes
SHA-1Yes
SHA-256Yes
CRC-32No. The data contains CRC-32 values, but CRC-32 is not a strong hash.

Cadence: NIST publishes a full Release in March. NIST publishes Delta releases in June, September and December. /health shows the Release and Delta releases that the service uses.

Quickstart

Start the service.

The test suite uses test data. It does not use the NIST data. For real lookups, you must download approximately 19 GiB one time. You must have approximately 260 GiB of free disk space.

Run the tests

Build the image and run the test suite. The suite also starts the service one time with test data.

docker-compose -f docker-compose.build.yml up --build api-test

Prepare the Hash Set

This command downloads the Release and the Delta releases. It does the three integrity checks and builds the index. It writes rds.db and the manifest into ./data. Put the Delta releases in order, oldest first.

make provision RELEASE=2026.03.1 DELTAS="2026.06.1 2026.09.1"
make verify

Start the service

Start the API on port 5000. Make sure that /health shows "ready": true. Then send the digests.

docker-compose -f docker-compose.prod.yml up -d api
curl -s localhost:5000/health
API

API endpoints.

POST/check

Send one Algorithm and one or more Digests. The service returns one result for each digest: known, unknown or invalid.

2004xx rejected503 not ready
GET/health

Shows the Set, the Release, the Delta releases, the final dbhash and a ready flag. Examine this data before you use the results.

GET/ping

Returns {"result": "pong"} when the service operates. This endpoint operates without a Hash Set.

Operate your own service.

cybagard does not supply a public server. You prepare and verify the data. You operate the service. The service records each lookup.
