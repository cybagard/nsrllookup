Why nsrllookup

Separate the benign from the interesting.

Most files in a digital-evidence corpus are pre-existing reference data. nsrllookup marks those digests as known so you can set them aside, and every answer says where it came from.

01

Provenanced answers

Every result names the Set, the Release, the Delta releases applied, and the final dbhash. That is enough to check the answer against NIST yourself.

02

Integrity in three layers

The archive SHA-1, each inner file's SHA-256, and NIST's dbhash are all verified. If any layer fails, the Hash Set is never served.

03

Public, but accountable

Lookups need no login. Every session, accepted or rejected, is written to an append-only Audit Trail.

04

No daemon, no RAM set

One WSGI service reads a verified, read-only database. Each lookup is an indexed seek on disk.

Lookup Result

An answer you can re-verify.

Send one Algorithm and any number of Digests. Each digest gets its own result, with the full dataset lineage attached.

  • ✓MD5, SHA-1, SHA-256. Any letter case, normalised to uppercase.
  • ✓Per-item invalid. A digest that doesn't parse never fails the whole batch.
  • ✓Readiness gate. If the manifest is missing or doesn't match, the service returns 503 and answers nothing.
POST /check
$ curl -s -X POST localhost:5000/check \
    -H 'Content-Type: application/json' \
    -d '{"algorithm":"sha256","hashes":["ad7b9c14…"]}'

Provisioning

Three rings of trust.

The Provisioner checks every layer and records all three values in a Provisioning manifest. At startup the service is ready only if that manifest still matches the mounted Hash Set.

1

Archive SHA-1

The downloaded release archive must match NIST's published .sha sidecar.

2

Inner-file SHA-256

Every file inside the archive is checked against signatures.txt.

3

Final dbhash

Once all deltas are applied, the database must match NIST's published dbhashes.txt for the last Release.

NSRL coverage

Quickstart

From zero to a verified answer.

You can run the fixture-based test suite with no data at all. Serving real lookups needs a one-time download of about 19 GiB and roughly 260 GiB of free disk at peak.

Try it without any data

Build the image and run the self-contained suite, including an end-to-end boot smoke test.

docker-compose -f docker-compose.build.yml up --build api-test

Provision the Hash Set

Fetch the Release and its Delta releases (oldest to newest), verify all three layers, build the index, and write rds.db and the manifest into ./data.

make provision RELEASE=2026.03.1 DELTAS="2026.06.1 2026.09.1"
make verify

Serve and look up

Start the API on port 5000 against the mounted volume, check provenance, then send digests.

docker-compose -f docker-compose.prod.yml up -d api
curl -s localhost:5000/health
API

Three endpoints.

POST/check

One Algorithm with one or more Digests. Returns one Lookup Result per digest: known, unknown or invalid.

2004xx rejected503 not ready
GET/health

The loaded Set, Release, Delta releases and final dbhash, plus a ready flag. Check this before you trust any answers.

GET/ping

A simple liveness probe that returns {"result": "pong"}. Works without a Hash Set.

Run your own reference.

There is no hosted endpoint. You provision and verify your own dataset and run your own instance, and every lookup is audited.
